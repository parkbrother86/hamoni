# 용량 지표 읽는 법 — 용어 정의

측정 수치를 잘못 읽으면 인프라 판단이 통째로 틀어진다. 이 문서는 `flood.py`
출력과 [README.md](README.md) 실측표의 **용어를 정확히 정의**한다.

실측 근거는 README.md, 전체 연구 맥락은 개발기 `bench/RESEARCH.md`.

---

## 1. "슬롯"이 뭔가 — 슬롯 1개 = 동시에 1건

**슬롯은 "동시에 몇 건까지 처리 중일 수 있는가"의 칸 수다.**
슬롯 1개에는 **1건만** 들어간다. 100건이 아니다.

식당 테이블로 보면 정확하다:

```
슬롯 16개 = 테이블 16개
손님(채팅)은 줄 서서 무한히 대기
테이블이 비면 다음 손님이 즉시 앉는다
```

### 처리량은 슬롯 수가 아니라 나눗셈으로 나온다

```
처리량 = 슬롯 수 ÷ 1건당 소요시간
```

실측이 이 식과 정확히 맞는다 (fan-out 3, Tri-1.8B):

| 슬롯 | 1건당 평균 | 계산 | 실측 |
|---:|---:|---|---:|
| 16 | ~0.15초 | 16 ÷ 0.15 = **107/s** | **102~107/s** ✅ |
| 32 | ~0.76초 | 32 ÷ 0.76 = **42/s** | **42.1/s** ✅ |

**따라서 "16슬롯 = 초당 1,600건"은 틀렸다.** 슬롯당 초당 100건이 아니라,
슬롯 16개가 각각 0.15초씩 걸려 **합쳐서 초당 약 107건**이다.

### 슬롯을 늘리면 왜 오히려 느려지나

위 표가 답이다 — 슬롯을 2배(16→32)로 늘렸더니 **1건당 시간이 5배**
(0.15→0.76초)가 됐다. GPU 하나를 더 많은 요청이 나눠 쓰기 때문이다.
그래서 32÷0.76 < 16÷0.15. **테이블을 늘려도 주방이 하나면 음식이 늦게 나온다.**

| 흔한 오해 | 맞나 | 왜 |
|---|---|---|
| 슬롯 1개에 여러 건을 넣는다 | ❌ | 슬롯 1개 = 동시 1건 |
| 슬롯 16개면 처리량이 16배 | ❌ | 처리량 = 슬롯 ÷ 1건당 시간. 슬롯이 늘면 1건당 시간도 늘어난다 |
| 배치 크기가 N | ❌ | 배치가 아니다. N건이 **독립 HTTP 요청**으로 들어가고, 배칭은 vLLM 이 서버 안에서 알아서 한다(continuous batching) |
| 유저 N명이 동시 접속 | ❌ | 유저 수와 무관하다. 유저가 1,000명이든 10명이든 GPU 에 물리는 건 N건 |
| **채팅은 무한히 밀려오는데 N건까지만 동시 처리** | ✅ | 이것이다 |

실제 서비스로 옮기면:

```
유저 채팅 무한히 도착
      ↓
  [번역 서버 큐]   ← 초과분은 여기서 대기 (평균 수십 ms)
      ↓
   슬롯 N개        ← 여기만 통과 (admission control)
      ↓
     GPU (vLLM)
```

유저 1,000명이 동시에 떠들어도 GPU 에는 항상 N건만 물린다. 나머지는 큐에서
짧게 기다린다 — 초당 100건을 처리하므로 대기는 밀리초 단위다.

## 2. 슬롯을 늘리면 왜 더 느려지나 (실측)

| 동시 슬롯 | 입력 채팅/s | p95 |
|---:|---:|---:|
| 8 | 58.2 | 185ms |
| **16** | **102.4** | **179ms** |
| 32 | 42.1 ↓ | 1,189ms |

**슬롯 32는 처리량이 반토막나고 지연이 6배가 된다.** §1 의 나눗셈이 이유다 —
슬롯이 늘면 1건당 시간이 더 크게 늘어난다. vLLM 공식 벤치의 `inf`(무제한 투입)
실험도 같은 방향이었다 — 처리량이 165 → 133 req/s 로 **깎였다**.

**덜 넣는 게 더 빠르다.** admission control 이 안전장치가 아니라 성능 최적화인
이유이고, 번역 서버가 캐시일 뿐 아니라 **load regulator** 여야 하는 이유다.

## 3. 지표 사전

| 지표 | 정의 | 주의 |
|---|---|---|
| **입력 채팅/s** | 유저가 친 메시지 기준 처리율. fan-out 완료(모든 타겟 번역 끝)까지 세어야 함 | **제품 용량은 이 숫자** |
| **API req/s** | GPU 에 실제로 간 요청 수. fan-out 3 이면 채팅 1건당 3 | 인프라 튜닝용 |
| **동시 N (in-flight)** | 동시 처리 슬롯. §1 참조 | 유저 수 아님 |
| **도착률 (arrival rate)** | 초당 들어오는 요청 수. 처리 능력과 무관하게 발생 | open-loop 측정에서 씀 |
| **처리율 (throughput)** | 초당 완료된 수 | 도착률 > 처리율이면 큐 적체 |
| p50 / p95 | 응답 시간 중앙값 / 상위 5% | SLA 판정은 p95 |
| 달성률 | 처리율 ÷ 도착률 | 95% 미만이면 knee 넘음 |

## 3.5. 파라미터 사전 — 어느 게 무슨 일을 하나

이름이 비슷해서 헷갈리기 쉽다. **"누가 무엇을 제한하는가"** 로 나누면 명확하다.

### 클라이언트 쪽 (`flood.py` — 부하를 *만드는* 쪽)

| 파라미터 | 제한하는 것 | 비유 |
|---|---|---|
| `--concurrency N` | **슬롯 수** = 동시에 처리 중일 수 있는 건수 | 테이블 개수 |
| `--rps R` | **도착률** = 초당 새로 밀어넣는 수 (open 모드, 백프레셔 없음) | 손님이 들어오는 속도 |
| `--fanout en,jp,cn` | 채팅 1건이 만드는 **API 요청 수** (여기선 3) | 1인분 주문이 접시 3개 |
| `--duration` | 측정 시간(초) | — |
| `--max-concurrency` | ramp 모드가 시도할 슬롯 수 **상한** | — |
| `--break-p95` | 이 p95(ms) 넘으면 SLA 이탈로 보고 중단 | — |

> `--concurrency`(슬롯)와 `--rps`(도착률)는 **동시에 쓰지 않는다.** 슬롯을
> 정하면 도착률은 결과로 따라오고(closed-loop), 도착률을 정하면 슬롯은
> 결과로 따라온다(open-loop). §4 참조.

### 서버 쪽 (`vllm serve` — 부하를 *처리하는* 쪽)

| 파라미터 | 제한하는 것 | 실측에서 걸렸던 일 |
|---|---|---|
| `--max-num-seqs` | vLLM 이 동시에 굴릴 **시퀀스 수 상한** | 128 로 설정. 우리 부하에선 병목 아니었음 |
| `--max-num-batched-tokens` | **한 iteration 의 토큰 예산** | **2048 이 진범.** 슬롯 64 × 프롬프트 60토큰 = 3,840 이 예산 초과 → 붕괴. 8192 로 올려 해결 |
| `--max-model-len` | 요청 1건의 최대 길이(프롬프트+출력) | 1024. 짧을수록 KV 여유 ↑ |
| `--gpu-memory-utilization` | KV 캐시에 쓸 VRAM 비율 | 0.85. KV 는 5.9% 밖에 안 써서 여유였음 |

**클라이언트 슬롯과 서버 파라미터의 관계**: 클라이언트가 슬롯 16(fan-out 3)을
쓰면 서버에는 **API 요청 48개**가 동시에 도착한다. 서버의
`max-num-batched-tokens` 는 그 48개의 **프롬프트 토큰 합**을 감당해야 한다
(48 × 60 = 2,880 토큰). 이 계산이 안 맞으면 §2 의 붕괴가 난다.

## 4. closed-loop vs open-loop — 왜 둘 다 재나

| | closed-loop (`ramp`/`sustain`) | open-loop (`open`/`sweep`) |
|---|---|---|
| 방식 | 슬롯 N개 유지, 하나 끝나면 다음 투입 | 처리 능력과 무관하게 초당 R개 계속 발사 |
| 백프레셔 | **있음** (슬롯이 자연 제한) | **없음** |
| 답하는 것 | **처리량 상한**과 최적 슬롯 수 | **한계 도착률** — 큐가 터지는 지점 |
| 실제 대응 | admission control 이 걸린 우리 서비스 | 그게 없을 때의 트래픽 폭주 |

둘 다 필요하다. closed-loop 만 보면 "슬롯 제한이 있으니 안전"이라는 전제가
깔려서, admission control 없이 배포했을 때의 붕괴를 못 본다.

## 5. 측정할 때 반드시 확인할 것

**클라이언트가 병목이 아님을 먼저 증명한다.** 이 연구에서 세 번 "GPU 한계"로
오인했고 세 번 다 아니었다 (상세: README.md §측정 함정):

1. llama-cpp-python 서버 직렬화 → vLLM 대비 **10배** 차이
2. Windows→WSL2 클라이언트 병목 → 서버는 KV 0.9% 로 놀고 있었음
3. `max_num_batched_tokens=2048` → KV 캐시 문제로 오인

`flood.py` 는 이제 **클라이언트 관측(in-flight)과 서버 지표(`/metrics` 의
running/waiting/KV/preempt)를 함께** 찍는다. **둘이 벌어지면 서버 포화가
아니다** — 클라이언트나 네트워크를 의심할 것.

```
클라 in-flight 6,255 · p50 68초   ← 클라가 막힘
서버 running 3~8 · queue 0 · KV 0.9%  ← GPU 는 놀고 있음
```

## 6. 이 숫자를 제품 용량으로 옮길 때

- **유저 수 ≠ 부하.** 부하는 `동시 접속자 × 분당 발화 수`다. 1,000명이 분당
  1회 치면 16.7 채팅/s 이고, 이는 측정된 100/s 의 6분의 1이다.
- **수신자 수는 부하가 아니다.** 350명 채널이든 타겟 언어 수만큼만 번역한다
  (언어 3개면 3회).
- **번역 캐시가 앞단에 있다.** 반복 문구는 GPU 에 가지도 않으므로 실제 GPU
  요청은 위 수치보다 적다.
- **출력 길이에 반비례한다.** 이 GPU 의 천장은 출력 ~3,000 tok/s 부근이므로,
  긴 문장 위주 워크로드면 req/s 는 그만큼 내려간다.
